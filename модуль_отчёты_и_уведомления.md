Ты работаешь внутри существующего проекта платформы ВЕТАИ. Твоя задача — спроектировать и реализовать модуль уведомлений и модуль отчётности как естественное продолжение текущего интерфейса и существующей архитектуры, а не как отдельное приложение.

Контекст и ограничения
- Используй существующий проект ВЕТАИ как базу.
- Не переписывай проект с нуля.
- Не переходи на PostgreSQL.
- Не внедряй полноценный RBAC.
- Не внедряй email / SMS / push как обязательную часть MVP.
- Не делай видеоаналитику зависимостью нового модуля.
- Не оставляй mock как default behavior, если можно использовать текущие данные и текущие сущности.
- Если Prisma / DB временно недоступны, используй аккуратный mock fallback или localStorage только как резерв.
- Все новые экраны и компоненты должны визуально соответствовать текущей версии ВЕТАИ: та же типографика, те же карточки, та же плотность интерфейса, те же кнопки, табы, бейджи, фильтры и отступы.
- У нас уже есть иконка уведомлений в header и раздел / шаблон под кнопку «Отчёты». Нужно доработать именно их, а не придумать параллельный интерфейс.
- Пока упрощённо все уведомления адресуются одному пользователю. Но архитектуру делай так, чтобы потом можно было расширить до нескольких пользователей без переделки половины системы.

Главная идея
Нужно реализовать два связанных модуля:

1. Модуль уведомлений
Это не “чатик” и не “лента событий”, а рабочий inbox / список действий и важных событий.
По нажатию на иконку уведомлений в header должен открываться отдельный экран или отдельное полноразмерное окно со списком уведомлений.
Каждое уведомление должно быть кликабельно и вести к первоисточнику внутри системы:
- карточка животного;
- карточка группы / секции;
- экземпляр отчёта;
- шаблон отчёта;
- batch интеграции / импорт;
- системное событие.

2. Модуль отчётности
Это библиотека шаблонов отчётов и список экземпляров отчётов, созданных по шаблонам.
Пользователь должен видеть шаблоны начиная от дневных и сменных и заканчивая недельными и месячными.
Отчёты должны быть связаны с уведомлениями: например, уведомление сообщает, что отчёт готов, не прошёл валидацию или требует формирования.

Что уже есть в проектной логике и что надо переиспользовать
Перед началом изучи кодовую базу и найди:
- sidebar;
- header с иконкой уведомлений;
- текущий раздел «Отчёты»;
- shared layout / card / badge / tabs / table / modal / drawer / chart components;
- prisma schema;
- текущие сущности Event / OperationRequest / IntegrationBatch / ReportTemplate / ReportInstance / ReportValidationIssue / ReportExportJob / ReportSubmission / ReportAuditLog;
- mockData / fallback patterns;
- current routes and navigation patterns.

Нельзя игнорировать текущую архитектуру.
Если для MVP уже существуют подходящие сущности, используй их.
Если не хватает только состояния прочтения уведомлений, добавляй минимальное расширение, а не новый “микросервис ради микросервиса”.

Что нужно реализовать

1. Доработать уведомления в header
- использовать существующую иконку колокольчика;
- добавить badge с количеством непрочитанных;
- по клику открывать отдельный маршрут или отдельное полноразмерное окно / screen-level overlay, а не маленький dropdown на 5 строк;
- новый маршрут предпочтительно:
  - /notifications
  или
  - /today
  выбери тот, который лучше встраивается в текущую архитектуру;
- если есть смысл, можно оставить быстрый preview-popover на 3–5 пунктов, но основным поведением должен быть переход на полноценный экран списка.

2. Реализовать модуль уведомлений как Inbox / Today
Модуль должен показывать:
- непрочитанные;
- все;
- требуют действия;
- по отчётам;
- системные.

Обязательные типы уведомлений MVP:
A. Операционные
- здоровье / осмотр;
- проблемы идентификации;
- отклонения по кормлению;
- просроченные действия;
- важные события по животному / группе / секции.

B. По отчётам
- пора сформировать отчёт;
- отчёт сформирован;
- отчёт не прошёл валидацию;
- экспорт готов;
- экспорт завершился ошибкой;
- отправка завершилась ошибкой;
- отчёт требует внимания.

C. Системные
- импорт завершён с ошибкой;
- импорт завершён с предупреждениями;
- источник данных не обновлялся;
- конфликт / дубли / отсутствие данных.

3. Реализовать модуль отчётности
Нужно доработать текущий раздел «Отчёты» так, чтобы он стал реальной библиотекой шаблонов и экраном работы с экземплярами отчётов.

Обязательные группы шаблонов в MVP:
- Дневные;
- Сменные;
- Недельные;
- Месячные;
- Регламентные / Служебные можно оставить как каркас или скрыть за табом.

Базовые шаблоны MVP:
- RPT_MORNING_BRIEF
- RPT_SHIFT_PARLOR
- RPT_WEEKLY_HERD
- RPT_MONTHLY_MANAGEMENT

Нужно переиспользовать существующий Report* каркас, а не строить параллельную “самописную” отчётность.

4. Поддержать связь уведомлений и отчётов
- уведомление по отчёту должно открывать конкретный ReportInstance или ReportTemplate;
- из карточки шаблона отчёта должен быть доступ к истории экземпляров;
- из экземпляра отчёта должен быть доступ к связанным уведомлениям / ошибкам / валидациям;
- из уведомления по ошибке импорта должен быть доступ к batch / интеграции;
- из уведомления по животному — к карточке животного;
- из уведомления по группе / секции — к карточке группы / секции.

5. Реализовать непрочитанные уведомления “как на GitHub”
Минимальная логика:
- каждое новое уведомление появляется как непрочитанное;
- открытие уведомления или явное действие пользователя делает его прочитанным;
- должно быть “отметить как прочитанное”;
- должно быть “отметить всё как прочитанное”;
- должно быть “показать непрочитанные с даты”;
- должно быть визуальное отличие unread vs read;
- должно быть состояние “взято в работу” и “закрыто”, если уведомление связано с действием.

Важно:
Сейчас все уведомления идут одному пользователю.
Но модель хранения должна быть расширяемой.
Если в БД допустимо минимальное расширение — введи отдельную сущность состояния пользователя по уведомлению, например:
- NotificationItem
- NotificationUserState
или эквивалент.
Если БД менять нельзя — используй fallback repository, но оставь интерфейсы так, чтобы потом заменить на persistence без переписывания UI.

6. Упростить логику для MVP
В MVP:
- один пользователь;
- один inbox;
- без сложных пользовательских настроек каналов;
- без email/SMS/push как обязательного функционала;
- in-app — основной источник истины;
- статусы:
  - unread
  - read
  - in_progress
  - done
  - dismissed
- для report-related уведомлений достаточно:
  - unread
  - read
  - archived

Подробные требования к UI

A. Header / top bar
Используй текущий header.
Нужно:
- иконка колокольчика;
- badge unread count;
- hover / focus state;
- active state при открытом модуле;
- при unread > 0 бейдж должен быть заметный, но не кричащий;
- если count > 99, показывать 99+.

Поведение:
- desktop: click → переход на отдельный экран /notifications;
- mobile: click → fullscreen sheet / page.

B. Экран уведомлений
Экран должен выглядеть как рабочий inbox, а не как “технический лог”.

Структура:
1) Верхняя строка
- Заголовок: “Уведомления” или “Сегодня”
- Подзаголовок: количество непрочитанных и дата последнего обновления
- Кнопки справа:
  - “Отметить всё прочитанным”
  - “Только непрочитанные” toggle
  - фильтр / сортировка
  - обновить

2) Панель фильтров
Горизонтальные tab / pill filters:
- Непрочитанные
- Все
- Требуют действия
- Отчёты
- Системные

Дополнительные фильтры:
- период;
- тип;
- приоритет;
- источник;
- статус;
- дата “с”;
- при наличии уже существующих фильтров проекта — встроить в них.

3) Основная область списка
Каждое уведомление отображается как карточка-строка со следующими зонами:
- цветная левая полоса по важности:
  - красный = critical
  - оранжевый = high
  - жёлтый = medium
  - серый / синий = info / system
- иконка типа;
- заголовок;
- краткое описание в 1–2 строки;
- источник:
  - Животное / Группа / Секция / Отчёт / Интеграция / Система
- secondary metadata:
  - дата / время;
  - сколько прошло времени;
  - batch/source если уместно;
  - статус;
- unread marker:
  - точка / жирный текст / подложка;
- быстрые действия справа.

Обязательные быстрые действия на карточке:
- Открыть источник
- Прочитано
- В работу (если actionable)
- Закрыть / Готово (если actionable)
- Скрыть / Архивировать
- меню “ещё”

Карточка должна быть полностью кликабельной по основной области.
Но быстрые действия должны работать отдельно и не конфликтовать с переходом.

4) Пустые состояния
Нужно сделать нормальные empty states:
- нет непрочитанных;
- нет уведомлений по фильтру;
- нет уведомлений по отчётам;
- нет системных ошибок.

Тексты должны быть человеческими, без техно-бреда.
Например:
- “Непрочитанных уведомлений нет”
- “По выбранным фильтрам ничего не найдено”
- “Ошибок по отчётам нет”

5) Loading / skeleton states
Нужны skeleton loaders:
- 6–8 строк карточек;
- серые плашки на месте текста;
- отдельный skeleton для верхней панели и фильтров.

6) Error state
Если уведомления не загрузились:
- компактный warning block;
- кнопка “Повторить”;
- если есть кэш / last known state — показывать его с пометкой “данные могут быть устаревшими”.

C. Детальный экран уведомления / связанного действия
Если в проекте уже есть detail panel / drawer — переиспользуй.
Если нет — сделай правую панель или отдельный route detail.

Структура:
- заголовок;
- приоритет / статус;
- источник;
- время создания;
- последнее обновление;
- кто / что создал;
- блок “Контекст”;
- блок “История”;
- блок “Комментарии”;
- блок “Связанные объекты”;
- блок быстрых действий.

Вкладки или секции:
- Контекст
- История
- Комментарии
- Вложения
- Связанные отчёты / batch / корова / группа

D. Экран отчётов
Нужно использовать существующий раздел “Отчёты”, визуально адаптировав его под текущий дизайн ВЕТАИ.

Структура экрана:
1) Верхняя часть
- заголовок “Отчёты”
- подзаголовок: “Шаблоны и экземпляры отчётов”
- primary action:
  - “Создать отчёт”
  или
  - “Сформировать отчёт”
- secondary actions:
  - экспорт списка;
  - история;
  - обновить.

2) Табы / категории шаблонов
Горизонтальные tabs:
- Все
- Дневные
- Сменные
- Недельные
- Месячные
- Регламентные
- Архив (опционально)

3) Список карточек шаблонов
Каждый шаблон — карточка в текущем визуальном стиле:
- иконка;
- название шаблона;
- код;
- назначение / короткое описание;
- периодичность;
- основные KPI;
- основной экспортный формат;
- статус:
  - активен

  - Сформировать

  - Открыть

Карточка должна быть визуально похожа на ваши текущие report cards, но информативнее и полезнее.

4) Экран шаблона отчёта
Нужно показать:
- название;

- описание;
- периодичность;
- аудиторию;

Нужно показать:
- период;

Статусы экземпляра:

Обязательные действия:

E. Визуальный стиль
Нужно выдержать интерфейс в текущем стиле платформы:
- светлый фон;
- аккуратные карточки;
- закругления как в текущих дашбордных карточках;
- умеренные тени;
- понятные статусные бейджи;
- никакого “кислотного enterprise UI”;
- нельзя делать экран визуально чужеродным относительно текущего дашборда.

UI-требования подробно:
- сетка 12 колонок на desktop;
- контейнер не должен быть чрезмерно узким;
- плотность интерфейса средняя: помещать много полезного, но без “мелкого текста для муравьёв”;
- у карточек шаблонов и уведомлений должна быть одна визуальная логика;
- вторичный текст делать менее контрастным, но читаемым;
- CTA-кнопки различать:
  - primary;
  - secondary;
  - ghost;
  - destructive;
- бейджи статусов:
  - unread
  - read
  - ready
  - failed
  - overdue
  - draft
  - archived

- “Отметить прочитанным”

Функциональные требования к данным и логике

1. Источники уведомлений
Используй текущие данные проекта там, где это уже есть:
- Event / CowEvent
- OperationRequest
- IntegrationBatch
- ReportValidationIssue
- ReportExportJob
- ReportSubmission
- ReportInstance
- возможно DashboardSnapshot / EventType / MilkRecord / FeedRecord как источник summary / derived alerts

2. Что считать actionable notification
Actionable notification — это элемент, который требует действия пользователя и должен позволять:
- открыть объект;
- перевести в “в работе”;
- закрыть;
- оставить комментарий;
- перейти в первоисточник.

Если уже есть OperationRequest — не дублируй его новой сущностью без причины.
Если нужно, строй inbox поверх OperationRequest + системных / report notifications.

3. Что считать report notification
Это уведомления, порождённые:
- расписанием отчётов;
- успешной генерацией;
- ошибками валидации;
- ошибками экспорта;
- ошибками отправки;
- отсутствием обязательных данных.

4. Правила непрочитанности
Нужно реализовать:
- unreadAt / readAt или эквивалент;
- filter unread only;
- mark one as read;
- mark all as read;
- read state persists between sessions;
- unread count updates after actions without full page reload.

5. Дедупликация
Нельзя плодить одинаковые уведомления без контроля.
Нужно предусмотреть deduplication по логике:
- тип;
- объект;
- временное окно;
- источник.

Если уже есть externalReference / event key / report key — используй их.
Если нет — создай helper, не раздувая систему.

6. Источник и кликабельность
Каждое уведомление должно иметь:
- sourceType
- sourceId
- sourceLabel
- route / deepLink

При рендере интерфейс должен уметь:
- показать источник текстом;
- показать иконку источника;
- открыть соответствующую страницу.

7. Шаблоны отчётов в MVP
Использовать как дефолтные шаблоны:
- утренний бриф;
- сменный отчёт по доению;
- недельный свод по стаду;
- месячный управленческий отчёт.

Под каждый шаблон показать:
- периодичность;
- аудиторию;
- ключевые KPI;
- рекомендованные визуализации;
- форматы экспорта.

8. Расписание отчётов
В MVP достаточно:
- показать расписание;
- дать возможность вручную сформировать;
- подготовить архитектуру под автогенерацию.

Если в текущем проекте автогенерации нет, не изобретай полноценный job scheduler.
Сделай:
- schedule config;
- UI каркас;
- mock / placeholder execution state;
- prepare hooks for future automation.

9. Fallback-поведение
Если backend не готов:
- уведомления должны открываться хотя бы на mock repository / local state;
- read/unread должен работать;
- шаблоны отчётов должны быть видны;
- генерация должна работать на mock / local fallback;
- UI не должен разваливаться.

Что нужно проверить перед реализацией
1. Как сейчас устроен header и как туда встроен колокольчик.
2. Как сейчас устроен раздел “Отчёты”.
3. Какие shared cards / tabs / badges / tables уже есть.
4. Есть ли уже operation detail / event detail / side panel.
5. Как в проекте устроены status colors.
6. Какие route patterns уже используются.
7. Есть ли mock pattern / repository pattern.
8. Какие Report* сущности уже реально используются, а какие только лежат в schema.

Критерии приёмки
Считать задачу выполненной, если:
- иконка уведомлений в header показывает unread count;
- по нажатию открывается полноценный экран уведомлений;
- уведомления разделены минимум на:
  - непрочитанные
  - все
  - требуют действия
  - по отчётам
  - системные
- у уведомления есть кликабельный источник;
- можно отметить уведомление прочитанным;
- можно отметить все уведомления прочитанными;
- read state сохраняется;
- раздел “Отчёты” показывает шаблоны и экземпляры;
- есть минимум 4 шаблона отчётов MVP;
- карточки шаблонов адаптированы под текущий UI ВЕТАИ;
- из уведомления по отчёту можно открыть отчёт;
- из отчёта можно увидеть связанные статусы / ошибки / историю;
- всё визуально выглядит частью текущей системы;
- код не ломает существующие страницы;
- при отсутствии БД есть fallback, но он не подменяет реальную работу там, где данные уже доступны.

Формат ответа после выполнения
После реализации покажи:
1. список созданных файлов;
2. список изменённых файлов;
3. краткое описание архитектуры;
4. краткое описание UI-решений;
5. что работает уже сейчас;
6. что оставлено каркасом на следующую итерацию;
7. команды для локальной проверки;
8. что проверить руками в UI.

Порядок работы
Выполняй задачу по шагам:
1. изучи текущую структуру проекта;
2. найди текущие shared components и routes;
3. определи, какие сущности можно переиспользовать;
4. спроектируй типы notification/reporting;
5. реализуй repository / mapping layer;
6. реализуй unread/read state;
7. собери экран уведомлений;
8. доработай экран отчётов;
9. свяжи уведомления и отчёты;
10. проверь fallback без обязательной БД;
11. проверь happy path;
12. собери итоговый список изменений.

Важно
Не пиши лишнюю теорию.
Не выдумывай новую платформу.
Не делай “идеальный enterprise-монолит будущего”.
Нужно аккуратно и реалистично довести до ума именно текущую версию ВЕТАИ:
- уведомления как рабочий inbox;
- отчёты как библиотека шаблонов и экземпляров;
- связка уведомлений и отчётов;
- минимальные клики;
- понятные статусы;
- кликабельные переходы к источнику.
