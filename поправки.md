# Промт для Codex/Antigravity: controlled demo data для Stage 1 без разъезда с реальным репозиторием

## Контекст

Используй существующий проект `vetai-platform` как базу и **не переписывай его с нуля**.

Цель этого задания: подготовить и/или доработать **контролируемый demo-layer** только там, где Stage 1 ещё не закрыт реальными данными, при этом:

- не ломать принцип **SQLite-first**;
- не включать mock по умолчанию;
- не подменять реальные сущности выдуманными моделями;
- не строить новые доменные абстракции без прямой необходимости.

Этот промт должен опираться на **реальные файлы репозитория**, а не на абстрактную идеальную схему.

## Обязательная проверка перед работой

### Важные уточнения по расхождениям

- В репозитории **нет** отдельной Prisma-модели `Group`; вместо неё используется `GroupUnit`.
- В репозитории **нет** модели `CowGroupHistory`; вместо неё используется `GroupMembership`.
- В репозитории **нет** модели `MilkBalance`; экран баланса молока сейчас собирается из `AfimilkDayMilk + EconomicFact`.
- В репозитории **нет** отдельной сущности `Economy`; для экономических фактов используется `EconomicFact`.
- Для коровы стабильный внутренний ключ маршрутизации — `cow.id`; внешний мастер-ID — `cow.afiId`.
- Для секций уже предусмотрены внешние коды: `externalCode`, `dtmCode`, `afiCode`.

Если для задачи требуется новая сущность, сначала докажи, что её нельзя закрыть текущими моделями. Иначе **не вводи её**.

## Опасности применения старого варианта промта

Ниже список того, чего делать нельзя, даже если это кажется быстрым путём к демо.

1. **Не вводить новые сущности поверх действующей схемы без необходимости.**
   Старый вариант провоцирует агента создавать `Group`, `CowGroupHistory`, `MilkBalance`, `Economy`, хотя в коде уже есть `GroupUnit`, `GroupMembership`, `EconomicFact`, `AfimilkDayMilk`.

2. **Не делать mock скрытым operational-слоем.**
   Demo-layer допустим только как явный слой, который можно включить/выключить; runtime API по умолчанию должны читать из SQLite.

3. **Не смешивать synthetic и real без маркировки.**
   Если добавляется synthetic-данные, укажи это явно в коде, документации и ответе.

4. **Не ломать существующие API-контракты.**
   Если уже есть маршрут `/api/groups/[id]` или `/api/milk-balance`, дорабатывай их вокруг текущей структуры ответа, а не перепридумывай весь API.

5. **Не строить аналитику на недоказанной истории membership.**
   В текущем коде история групп местами аппроксимируется через `Event` и текущее `groupId`. Не выдавай это за полностью достоверную историческую модель.

6. **Не предлагать новую обязательную миграцию там, где достаточно controlled seed/import.**
   Если задачу можно закрыть сидированием или дополнительным импортом в существующие таблицы, не расширяй схему ради удобства промта.

7. **Не уводить задачу в Stage 2.**
   Не тащи RBAC, PostgreSQL, видеоаналитику, новую экономическую подсистему или “идеальную нормализацию”, если задача про рабочее demo Stage 1.

## Что именно нужно сделать

### 1. Сначала провести audit `real / approximated / synthetic`

Перед реализацией раздели все нужные данные на три категории:

1. `real` — уже берутся из SQLite и подтверждены импортом/схемой;
2. `approximated` — могут быть вычислены из уже существующих таблиц;
3. `synthetic` — реально отсутствуют и требуют controlled demo-layer.

Это разделение нужно явно зафиксировать в ответе.

### 2. Использовать текущие сущности, а не выдуманные

Если нужен demo-layer, заполняй в первую очередь существующие таблицы:

- `GroupUnit`
- `Section`
- `GroupMembership`
- `CowSectionHistory`
- `GroupSectionHistory`
- `EconomicFact`
- при необходимости `Event`

Не создавать отдельные параллельные demo-таблицы, если существующая модель уже позволяет решить задачу.

### 3. Membership/history делать только как controlled approximation

Если для переходов Stage 1 не хватает истории:

- привязывай synthetic/history к **реальным** `Cow`, `GroupUnit`, `Section`;
- не меняй группы и секции хаотично по дням;
- делай редкие и объяснимые переводы;
- при наличии `FeedRecord` и DTM-контуров держи логику совместимой с ними.

Если достоверно восстановить историю нельзя, укажи это явно как `approximated`, а не как `real`.

### 4. Milk balance строить поверх текущей схемы

Для demo-ready milk balance используй:

- валовый объём из `AfimilkDayMilk.actualTotal`;
- потоки `milk_sold`, `milk_calves`, `milk_loss`, `milk_revenue` через `EconomicFact`.

Не создавай отдельную сущность `MilkBalance`, если задача только в том, чтобы показать рабочий экран и переходы.

### 5. Экономику не выделять в новую подсистему

Если для демо не хватает экономики:

- используй `EconomicFact`;
- допускается controlled synthetic для типов:
  - `milk_sold`
  - `milk_calves`
  - `milk_loss`
  - `milk_revenue`
  - при необходимости `feed_cost`
  - при необходимости `gross_margin`

Но не создавай новый модуль экономики с отдельной моделью, если это не требуется для текущего Stage 1.

### 6. Demo-layer должен жить в SQLite, но не быть default behavior

Если добавляешь demo-данные:

- они должны грузиться в SQLite;
- они должны включаться только явно;
- UI не должен читать mock напрямую из фронтенда как основной источник;
- runtime API по умолчанию должны продолжать читать реальные таблицы.

### 7. Не ломать уже существующий env и API

При необходимости demo/fallback:

- сначала используй существующий `VETAI_ALLOW_MOCK`;
- не переименовывай рабочий флаг без причины;
- не меняй сигнатуры существующих API без явной пользы;
- не убирай `no_data`-сценарии там, где они уже предусмотрены.

## Что считается хорошим результатом

После выполнения задачи должно быть возможно показать demo Stage 1, не разъезжаясь с текущим кодом:

- dashboard;
- sections;
- group card;
- herd / cow card;
- feeding;
- milking / milk balance;
- events;
- integrations / batches.

И при этом:

- маршруты используют реальные внутренние ID;
- synthetic-слой честно отделён от real;
- API остаются SQLite-first;
- новые сущности не добавлены без необходимости;
- в ответе явно перечислены риски, ограничения и места, где данные только approximate.

## Ограничения

- не переходить на PostgreSQL;
- не переписывать проект с нуля;
- не вводить полноценный RBAC;
- не тащить видеоаналитику в критический путь Stage 1;
- не подменять всю систему глобальным mock;
- не оставлять mock как поведение по умолчанию;
- не маскировать approximate/synthetic данные под fully real.
