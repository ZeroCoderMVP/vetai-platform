# AGENTS.md

## Назначение
Этот файл обязателен к прочтению перед началом любой работы в репозитории **VETAI / vetai-platform**.
Он задаёт базовые правила для Codex: как понимать проект, какие архитектурные решения уже приняты, что считается текущим приоритетом, как обращаться с данными, документацией и запросами на уточнение.

Главная цель агента: **помогать довести Stage 1 до рабочего операционного контура**, а не расползаться в бесконечную “идеальную платформу будущего”.

---

## 1. Контекст проекта

Проект — внутренняя платформа для молочной фермы.
Основной контур Stage 1:
- загрузка данных из файловых источников в SQLite;
- единая внутренняя модель объектов;
- базовые экраны и переходы;
- минимально полезная аналитика без сложного AI;
- почти полный уход от mock-заглушек на основных пользовательских экранах.

Система работает с такими основными доменами:
- стадо / животные;
- группы;
- секции / размещение;
- кормление;
- молоко / доения / баланс молока;
- события;
- интеграции и качество данных;
- отчёты.

### Что важно помнить
1. **Stage 1 ещё не закрыт.**
2. Сейчас нужен не “сверхархитектурный рефакторинг”, а последовательное снятие блокировок.
3. Главные блокировки связаны не только с UI, но и с организацией данных и ID.
4. В ближайшем горизонте проект остаётся на **SQLite**.
5. Основной вектор: **SQLite-first + ingestion from folders + stable routes by ID**.

## 2. Текущий приоритет

### Главная цель на ближайшие спринты
Убрать блокировки переходов и почти полностью уйти от mock на базовых экранах.

### Это означает
- все основные API читают **из SQLite**, а не из mock по умолчанию;
- файлы используются **только как вход для импорта**, а не как основной runtime-источник UI;
- переходы строятся по **стабильным ID**;
- данные AFI / DTM / AIC должны быть один раз нормально загружены в SQLite;
- для коров, групп, секций и событий должна существовать реальная навигационная модель.

---

## 3. Ключевые архитектурные принципы

### 3.1. SQLite-first
До отдельного решения владельца проекта:
- SQLite считается основным operational storage;
- UI и API должны опираться на SQLite;
- папки с файлами используются для ingestion pipeline;
- прямое чтение папок из runtime-API допускается только как временный fallback и должно быть явно помечено.

### 3.2. No mock by default
На базовых экранах mock **не должен быть поведением по умолчанию**.

Допустимо:
- отдельный dev fallback;
- явный feature flag;
- временная заглушка для не приоритетного модуля.

Недопустимо:
- тихая подмена real data на mock без явного сигнала пользователю;
- смешение mock и real data внутри одного сценария без маркировки.

### 3.3. Route by ID, context by query
Маршруты строятся так:
- `path` определяет **главный объект страницы**;
- `query params` хранят **контекст перехода**.

Примеры:
- `/herd/42`
- `/groups/7?dateFrom=...&dateTo=...`
- `/sections/12?from=map&dateFrom=...`
- `/events/114`

Использование:
- `path`: только сущность страницы;
- `query`: период, источник перехода, фильтры, текущая группа, текущая секция, активный tab.

### 3.4. Стабильные внутренние идентификаторы
Внутренний UI не должен опираться на случайные отображаемые поля.

Нужно использовать:
- `cow.id`
- `group.id`
- `section.id`
- `event.id`
- `operation.id`
- `report.id`

Master ID по животным: **AFI ID**.

## 5. Папки входящих файлов и ingestion

Проект должен использовать файловую инфраструктуру примерно такого вида:

```text
/data
  /inbox
    /afimilk
    /dtm
    /aic
  /processed
    /afimilk
    /dtm
    /aic
  /error
    /afimilk
    /dtm
    /aic
  /archive
```

### Правила обработки
1. Новый файл попадает в `inbox/<source>`.
2. Import job подбирает его.
3. Создаётся запись `IntegrationBatch`.
4. Данные парсятся и пишутся в SQLite.
5. Успешный файл переносится в `processed`.
6. Ошибочный файл переносится в `error`.
7. При необходимости файл архивируется.

### Что логировать в IntegrationBatch
Минимум:
- `source`
- `filename`
- `fileHash`
- `startedAt`
- `finishedAt`
- `status`
- `recordsRead`
- `recordsInserted`
- `recordsUpdated`
- `recordsSkipped`
- `errorMessage`

## 6. Источники данных Stage 1

### 6.1. Afimilk
Формат: JSON-отчёты.
Основное значение:
- животные;
- health / reproduction / calving события;
- сигналы по животным.

### 6.2. DTM
Формат: Excel.
Основное значение:
- кормление;
- mix batches;
- ingredient consumption;
- эффективность групп / загонов.

Ограничение:
- DTM не даёт ID коров;
- DTM работает на уровне группы / секции / загона.

### 6.3. AIC / Waikato
Формат: `.AIC`.
Основное значение:
- доения;
- молочный контур.

## 7. Что считается критическим для Stage 1

### Должно работать
- загрузка AFI в SQLite;
- загрузка DTM в SQLite;
- загрузка AIC в SQLite;
- dashboard на реальных данных;
- карта секций / размещение;
- карточка группы;
- карточка коровы;
- кормление;
- доения / баланс молока;
- события;
- интеграции и quality status.

### Обязательные переходы
- секция → группа;
- группа → корова;
- корова → событие;
- рацион → секция;
- рацион → группа;
- баланс молока → группа доения;
- баланс молока → телята;
- баланс молока → экономика / корректировка.

## 8. Что пока не приоритет

Не уводить работу в сторону, если это не согласовано отдельно:
- полноценный production RBAC;
- сложная AI-аналитика;
- видеоаналитика как критический путь Stage 1;
- глубокие причинно-следственные модели;
- избыточный инфраструктурный рефакторинг;
- миграция на PostgreSQL без прямого решения владельца проекта.

## 9. Правила работы с кодом

### 9.1. Не делать большой несогласованный рефакторинг
Если задача локальная, решай локально.
Не переписывай полпроекта “заодно”.

### 9.2. Не менять доменную модель молча
Если вводится новая сущность или меняется смысл существующей — это должно быть явно отражено:
- в коде;
- в миграции;
- в короткой документации / changelog.

### 9.3. Не зашивать локальные пути
Недопустимо:
- `C:\Users\...`
- абсолютные локальные пути разработчика;
- зависимость от структуры диска конкретной машины.

Использовать:
- env variables;
- config;
- относительные пути проекта;
- системную папку `/data/...`.

### 9.4. Не смешивать runtime и import-логику
- import читает файлы и пишет в SQLite;
- runtime API читает SQLite;
- UI читает API.

### 9.5. Любая заглушка должна быть честно помечена
Если временно используется mock / placeholder:
- это должно быть явно обозначено в коде;
- не должно быть default mode для критических экранов Stage 1;
- в финальном отчёте агент должен указать это как неготовность.

## 10. Правила работы с документацией

### 10.1. Что обновлять обязательно
Если агент меняет архитектурно важную вещь, нужно обновить:
- `README.md` — если меняется запуск, структура данных, команды;
- `docs/` или `notes/` — если появляется новая схема данных, pipeline или маршрут;
- runbook / import guide — если меняется обработка файлов.

### 10.2. Документировать надо кратко, но по делу
Нужны не романы, а:
- что добавлено;
- почему;
- как запустить;
- что проверить.

### 10.3. Если решение временное — так и писать
Нельзя маскировать временную схему под окончательную.

## 11. Когда нужно запросить уточнение у человека

Агент обязан запросить уточнение, если упирается в одно из следующих мест:

1. неясно, что является master ID для группы или секции;
2. неясно, нужно ли новое поле/сущность или можно использовать текущую;
3. есть несколько равноправных трактовок бизнес-логики;
4. неочевидно, входит ли модуль в Stage 1 или это уже Stage 2+;
5. нет данных для честной реализации, и остаётся только гадать;
6. расчёт метрики требует бизнес-решения, а не инженерной догадки.

Если нет ясности, агент должен писать прямо:
**"требуется уточнение"**.

## 12. Формат выполнения задач

Перед началом задачи агент должен:
1. определить, какой домен затрагивается;
2. перечислить затрагиваемые файлы;
3. понять, есть ли зависимость от миграций / данных / env;
4. проверить, не опирается ли текущий экран на mock.

Во время задачи агент должен:
1. делать изменение минимально достаточным;
2. не ломать существующие сценарии;
3. сохранять совместимость, если это разумно;
4. писать код так, чтобы его можно было проверить локально.

После задачи агент должен:
1. перечислить, что сделано;
2. перечислить, что не сделано;
3. перечислить, что требует ручной проверки;
4. указать, какие команды запускать для проверки;
5. если нужно — обновить документацию.

## 14. Definition of Done для задач Stage 1

Задача считается доведённой до полезного состояния, если:
- код собран логически и не размазан по случайным местам;
- данные приходят из SQLite, если это основной пользовательский сценарий;
- mock не является скрытым default behavior;
- переходы строятся по реальным ID;
- есть понятная ручная проверка;
- документация обновлена, если это необходимо.

---

## 15. Нежелательные паттерны

Избегать:
- “сначала красиво на UI, потом как-нибудь привяжем к данным”;
- чтения папок из пользовательского API как основного режима работы;
- большого количества магических констант и хардкодов;
- локальных абсолютных путей;
- смешения demo / prod поведения без явной маркировки;
- создания сущностей без чёткого понимания, как по ним будет строиться навигация.

---

## 16. Главный принцип

Если коротко:

> Сначала реальные сущности, реальные ID, реальные данные в SQLite и реальные переходы.
> Потом всё остальное.

Если в результате работы экран всё ещё красивый, но не может честно открыть объект по ID — задача не доведена.
