# ВЕТАИ — запросы к Codex по блокам для снятия блокировок переходов и ухода от mock

Этот файл нужен как набор **последовательных запросов к Codex**. Их лучше отправлять **по одному блоку**, а не одним гигантским сообщением, иначе даже хороший агент начинает творить человеческое.

## Общие вводные для Codex

Используй существующий проект `vetai-platform` как базу. Цель текущего цикла — не "сделать всю платформу", а:

1. перевести ключевые экраны на **SQLite-first**,
2. организовать **разовый backfill** из файлов,
3. снять блокировки переходов,
4. почти полностью убрать **mock** с базовых экранов Stage 1.

### Что считаем Stage 1 baseline

Должны работать экраны и переходы:
- dashboard;
- секции / карта местности;
- группа;
- карточка животного;
- кормление;
- молоко / баланс молока;
- события;
- интеграции / batches.

Переходы, которые нужно разблокировать:
- секция → группа;
- группа → корова;
- корова → событие;
- рацион → секция;
- рацион → группа;
- баланс молока → группа доения;
- баланс молока → телята;
- баланс молока → экономика / продажа.

### Ограничения и принципы

- Пока **остаемся на SQLite**.
- Папки с входящими файлами являются официальной инфраструктурой для импорта.
- UI должен читать из **SQLite**, а не напрямую из файловой системы.
- Mock допускается только как явный debug fallback, **не по умолчанию**.
- Везде, где это возможно, переходы строить по схеме:
  - `path` = главный объект страницы,
  - `query params` = контекст (`from`, `dateFrom`, `dateTo`, `groupId`, `sectionId`).

### Структура входящих файлов после распаковки

Предполагается, что файлы будут лежать в проекте так:


Дополнительно должны использоваться папки:

```text

/data/processed/dtm
/data/processed/aic
/data/error/afimilk
/data/error/dtm
/data/error/aic
```

   - mock включался только явно через env-переменную вида `VETAI_ALLOW_MOCK=1`;
   - если в SQLite нет данных, API возвращал пустой результат + статус `no_data`, а UI показывал понятное состояние "данные не загружены".

- при пустой БД пользователь видит `empty state`, а не фальшивую аналитику;
- в README описан режим SQLite-first;
- никаких абсолютных Windows-путей в основных экранах и API.

# Блок 3. Реализовать ingestion pipeline через папки inbox/processed/error

## Запрос к Codex

Сделай файловый ingestion pipeline для AFI, DTM и AIC с логированием в `IntegrationBatch` и переносом файлов между `inbox`, `processed` и `error`.

### Что нужно сделать

1. Реализовать единый сценарий импорта:
   - читать файлы из `/data/inbox/{source}`;
   - создавать batch в `IntegrationBatch`;
   - парсить данные;
   - писать нормализованные записи в SQLite;
   - переносить файл в `/data/processed/{source}`;
   - при ошибке переносить в `/data/error/{source}`.
2. Для каждого batch фиксировать:
   - `source`;
   - `filename`;
   - `fileHash`;
   - `startedAt` / `finishedAt`;
   - `status`;
   - `recordsRead` / `inserted` / `updated` / `skipped`;
   - `errorMessage`.
3. Сделать команды:
   - `npm run import:afimilk`
   - `npm run import:dtm`
   - `npm run import:aic`
   - `npm run import:all`
4. Проверить поддержку реальных файлов из предоставленных папок.

### Acceptance criteria

- каждый источник импортируется из своей папки;
- обработанные файлы переносятся в `processed`;
- ошибочные файлы попадают в `error`;
- в `IntegrationBatch` появляется полная история прогонов;
- `npm run import:all` проходит на предоставленных файлах.
