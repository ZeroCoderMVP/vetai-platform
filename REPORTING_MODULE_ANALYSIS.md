# Анализ и План доработки Модуля Отчетности (Reporting V2)

На основе проведенного аудита репозитория (`report_module.md`) определено текущее состояние модуля отчетности. База данных и фундамент слоя сервисов реализованы хорошо, однако модуль содержит множество заглушек (mocks), которые не позволяют использовать его в реальном операционном контуре (Stage 1).

Ниже приведен список того, что **реализовано (фундамент)**, и подробный план того, что **осталось сделать (заглушки и недоработки)**, с указанием приоритетов.

---

## 🟢 1. Резюме: Что уже готово (Фундамент)

1.  **Доменная модель (БД):** Схема данных Prisma полностью спроектирована для поддержки жизненного цикла отчета (Шаблоны `ReportTemplate` -> Секции `ReportSection` -> Строки/Метрики `ReportLine` -> Экземпляры `ReportInstance` -> Ошибки `ReportValidationIssue` -> Экспорт `ReportExportJob`).
2.  **Структура сервисов:** Выделено 7 микро-сервисов (`ReportTemplateService`, `ReportInstanceService`, `ReportGeneratorService` и др.), отвечающих за разделение логики.
3.  **Базовый API:** Эндпоинты для получения шаблонов (`/templates`), создания инстансов (`/instances`), запуска генерации и экспорта существуют и маршрутизируются правильно.
4.  **UI Каталога (Frontend):** Страница `/reporting` корректно загружает шаблоны из базы и фильтрует их по категориям (Регламентные, Племенные и т.д.).
5.  **Базовый Seed:** Скрипт сидирования создает 5 базовых шаблонов в БД.

---

## 🔴 2. Что осталось сделать (Технический долг и Mocks)

Модуль сейчас находится в состоянии "Mock/Demo". Чтобы перевести его в рабочую стадию (в соответствии с правилами `AGENTS.md` — *No mock by default*), необходимо выполнить следующие работы:

### Блок 1: Отказ от заглушек при генерации отчетов (ReportGeneratorService)
*   **Текущая проблема:** 5 builder-веток (BREEDING, REGULATORY, VETERINARY, PRODUCTION, MANAGEMENT) в `ReportGeneratorService` собирают данные с использованием хардкода или демо-данных, не обращаясь к реальным таблицам (напр., `Animal`, `MilkingSession`, `Event`).
*   **Задача:**
    1. Переписать логику каждой ветки (или как минимум наиболее критичных для MVP: *PRODUCTION* и *MANAGEMENT*) на реальные SQL/Prisma агрегации.
    2. Убрать генерацию "случайных" метрик. Данные должны браться строго из SQLite.

### Блок 2: Реальный Frontend на странице деталей отчета (`/reporting/reports/[id]`)
*   **Текущая проблема:** Страница деталей отчета заполняется mock-объектом через `setTimeout`, игнорируя реальные данные конкретного инстанса (экземпляра отчета) из базы.
*   **Задача:**
    1. Заменить мок-загрузку на реальный `GET /api/reporting/instances/[id]`.
    2. Реализовать связку UI с базой: отображать реальные `payloadJson` / `summaryJson` и историю `ReportValidationIssue`, полученные с бэкенда.
    3. Корректно передавать контекст фильтров (`?from=...&to=...`) при открытии отчета.

### Блок 3: Рабочий процесс Утверждения и Экспорта (Export & Submission)
*   **Текущая проблема:** Кнопка «Утвердить» вызывает только `alert()`. Сервис экспорта создаёт фиктивный URL, файл физически не генерируется ни в Excel, ни в PDF.
*   **Задача (отложена или MVP-версия):**
    1. **Утверждение:** Реализовать вызов `ReportSubmissionService` для изменения статуса инстанса (напр., на `APPROVED` / `SUBMITTED`) по кнопке "Утвердить".
    2. **Экспорт (если критично для Stage 1):** Настроить минимальную генерацию CSV/Excel (с помощью библиотек вроде `xlsx`) на основе `payloadJson`, отвязав от mock-URL.
    
### Блок 4: Управление шаблонами (Templates UI)
*   **Текущая проблема:** Кнопка «Создать шаблон» в каталоге не имеет обработчика и бизнес-логики под капотом.
*   **Задача (Низкий приоритет):**
    1. Для Stage 1 это можно отложить, если 5 захардкоженных шаблонов достаточно. В противном случае — создать UI для сборки `ReportTemplate` (указание метрик, формул, секций).

## 📝 3. Соответствие правилам проекта (AGENTS.md)

Исходя из документа `AGENTS.md`, текущее состояние модуля отчетности **нарушает правило 3.2 ("No mock by default")** и приоритет **"Минимально полезная аналитика на реальных данных"**.

Оставлять "демо" цифры недопустимо. Если реальных данных для формы нет (например, племенные индексы при отсутствии API Selex), экран должен прямо сообщать об отсутствии данных, а не генерировать заглушки.

## 🚀 4. План действий (Roadmap) на ближайшие спринты

1. **Step 1:** Удаление таймаутов и Mocks на фронтенде -> Привязка экрана отчета (`/reporting/reports/[id]`) к API `ReportInstanceService`.
2. **Step 2:** Перевод 1-2 главных отчетов (например, PRODUCTION/FEED или MGMT-HERD) на реальные Prisma-агрегации в `ReportGeneratorService`.
3. **Step 3:** Настройка кнопки "Утвердить" (переход статусов).
4. **Step 4 (Уточнить бизнес-ценность):** Реализация настоящего Excel-экспорта, если файлы нужны пользователю уже сейчас (а не просто просмотр на экране).
